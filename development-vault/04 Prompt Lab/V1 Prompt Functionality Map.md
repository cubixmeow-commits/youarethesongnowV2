# V1 Prompt Functionality Map

This note is the working-vault map of the recoverable Arcana V1 prompt system.

## The important finding

V1 did not have one prompt. Prompt behavior came from five different places:

1. **Source-static** — hardcoded PHP templates/directives.
2. **Runtime-assembled** — PHP compiled Song DNA, portraits, options, style and policy into the image prompt.
3. **Database-stored** — later static visual styles lived in `arcana_styles.prompt_text` and could be edited through the admin style manager.
4. **Model-generated** — Song DNA, Band Visual DNA and StyleMap were generated by text-model stages.
5. **Fallback mutations** — retry attempts rewrote/simplified the image request after failures.

## Historical evolution

The prompt system appears to have evolved in a clear sequence:

```text
Large PHP style catalog
        ↓
Database-managed static styles
        ↓
Dynamic Band Visual DNA
        ↓
Generated StyleMap
```

That matters for V2 because the final database layer was not a replacement for the whole creative engine. It externalized one important prompt family — visual style directives — while Song DNA, prompt compilation, portrait rules, safety rules and retry behavior remained distributed through application code and model-generated artifacts.

## Functional pipeline

```text
Artist + Song + Lyrics
        ↓
Song DNA analysis
        ↓
12-field structured interpretation
        ↓
Base cinematic prompt compiler
        ├─ portrait role
        ├─ custom instructions
        ├─ aspect / technical rules
        └─ safety / branding
        ↓
Style path
        ├─ none
        ├─ DB static style
        └─ Band Visual DNA → StyleMap
        ↓
Image provider
        ↓
7-step retry / safety mutations
```

## Database prompt note

The final V1 design definitely stored static style prompt text in the database. The admin handler exposes CRUD for:

- `style_key`
- `name`
- `prompt_text`
- `category`
- `sample_image_url`
- `is_active`
- `sort_order`
- `created_at`

The newer worker loads `arcana_styles.prompt_text` for the selected style. This means a meaningful portion of final prompting could be changed without editing PHP.

The repository does **not** prove every final production DB row without a database export, but the older `arcana.queue.processor.php` preserves a very large inline style catalog that appears to be a strong predecessor to the database-managed version.

## Legacy style catalog

The inline catalog contains dozens of presets across:

- cinematic / photoreal;
- painting / ink / collage;
- cyberpunk / sci-fi / fantasy;
- vaporwave / synthwave;
- punk / grunge / hip-hop;
- jazz / gothic / dreamcore;
- era/genre hybrids from the 1920s through 2020s;
- special dynamic album-art and historical-performance analysis modes.

A large number already use a proto-schema like:

- `STYLE`
- `MEDIUM`
- `COLOR`
- `LIGHTING`
- `SURFACE`
- `MOTION`
- `COMPOSITION`
- `AVOID`

That is useful evidence for V2 prompt design because the project had already started separating visual direction into structured concerns before the rebuild.

These prompts are valuable research material, not code we need to copy verbatim.

## What is recoverable even without the production database

We can reconstruct the **functionality** of the V1 prompt system from source even if the exact final DB values are unavailable:

- which stages existed;
- which stage owned song interpretation;
- how portrait identity was inserted;
- how visual styles were selected and applied;
- how user instructions were merged;
- how prompts were compiled for the image model;
- how retries progressively modified the request;
- where database-managed prompts entered the pipeline.

So V2 does not need to reverse-engineer V1 by copying old prompt strings. We can rebuild the behavior as explicit, versioned contracts.

## What a final V1 database export would add

If the final production database can be recovered, extract the `arcana_styles` records and compare them against the legacy PHP catalog. That would let us recover the exact final style library, including styles that were edited, disabled, reordered, added, or removed late in V1.

The highest-value fields are:

```text
style_key
name
prompt_text
category
is_active
sort_order
created_at
```

This would likely complete the historical style-prompt recovery almost entirely.

## Strong behaviors to preserve

- understand the song before asking for pixels;
- structured Song DNA;
- make uploaded people protagonists rather than passive references;
- concrete cinematography language;
- soft user steering;
- curated + dynamic visual identity;
- controlled fallback rather than immediate failure.

## Weak behavior to redesign

- mega-prompt conflicts;
- exact portrait match vs “no recognizable real people”;
- branding vs “no text”;
- silent portrait removal on retries;
- mutable DB prompts without revision history;
- multiple worker variants as competing prompt truth;
- old model-specific hacks.

## V2 implication

Treat prompts as versioned product behavior. Separate interpretation, narrative planning, visual identity, portrait identity, compilation and retry policy into distinct artifacts. Database-backed prompt components can still be useful, but they should have revision history and explicit provenance rather than silently becoming mutable global behavior.
