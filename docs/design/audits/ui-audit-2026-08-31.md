## 4. Responsive breakpoints and mobile behavior

| Band | Behavior |
| --- | --- |
| Phone | Bottom tabs, single column, safe-area padding, 48px touch targets (mostly) |
| Tablet 600–899 | Wider grids; **still bottom nav** (aligned with design intent) |
| Desktop ≥900 | Left rail, Create 2-col sticky summary, desktop atmosphere assets |

**Mobile strengths:** `viewport-fit=cover`, `100svh`, safe-area insets, 16px inputs (no iOS zoom), progressive Create disclosure, phone-specific backdrop assets.

**Mobile risks:** See §5.

## 5. Desktop-first / Flutter-hostile patterns

| Pattern | Why it hurts mobile/Flutter |
| --- | --- |
| Masonry.js + imagesLoaded on `/showcase` | Web-only layout engine |
| Imperative carousel scroll math | Prefer Flutter list/page controllers |
| Sticky Create summary split | Needs explicit adaptive shells, not CSS-only assumption |
| Hover Ken Burns / gallery lift | Prefer press; gate with `(hover: hover)` |
| `backdrop-filter` chrome | Platform blur differs |
| Dual tab↔rail via CSS reposition | Flutter should model two navigation scaffolds explicitly |
| Mega `app.js` DOM coupling | Flutter must target API contracts, not DOM |
| Owner HTML tables | Admin web pattern; not mobile product UI |
| `vh` in some dialogs | Prefer `svh`/`dvh` consistency |

Overall CSS is **mobile-first** (`min-width` dominant) — good foundation. Hostility is concentrated in showcase masonry, hover polish, and Create desktop split assumptions.

## 6. Inconsistent components and styling

1. Three parallel style systems: **app** (product), **site** (cream marketing), **docs** (Meow Control purple) — only app is in scope for the product OS.
2. Legacy color aliases coexist with `--color-*`.
3. Hardcoded OKLCH in body/hero/reveal bypass tokens.
4. Multiple content max-widths (1120 / 1200 / 1280 / 920) vs `--app-max`.
5. Button variants include one-offs (`--retrieve`, `--generate`).
6. Portrait grid column rules redefined twice in CSS.
7. Gallery empty state always `aria-hidden="true"` even when visible.
8. Image delete uses `confirm()`; portrait delete uses styled dialog.
9. Guest nav omits Showcase despite it being a major marketing surface.
10. Broken showcase tile focus outline: `outline` set to `--focus-ring` (a box-shadow value).

## 8. Accessibility problems

**Strengths:** skip link, `lang`, `aria-current` on nav, many wrapped labels, showcase dialog labeling, carousel keyboard + live region, portrait `aria-pressed`/`aria-label`, reduced-motion and prefers-contrast hooks, theme-color / apple web app meta.

**Issues (priority-ordered)**

1. Create missing real `<h1>` (title is a `<p>`; stages start at `h2`).
2. Gallery empty `aria-hidden="true"` while visually shown — AT users miss empty UX.
3. Showcase focus ring broken (invalid outline color).
4. Style listbox lacks keyboard listbox pattern (click-only).
5. Portrait delete dialog: no explicit focus move/restore (showcase does better).
6. Image delete `confirm()` inconsistent and less controllable.
7. Tertiary text / secondary nav opacity may fail contrast for small labels.
8. Session progress steps at 36px height — below 44–48px touch guidance.
9. No focus management when revealing People/Direction or paywall panels.
10. Owner dashboard dumps raw JSON in `<pre>` — poor structure for AT.
11. Labels rely on wrapping without `for`/`id` — brittle if markup splits.
12. Create summary `aria-live` on whole aside may over-announce.

Acceptance contracts target WCAG 2.2 AA — these gaps should be Phase 2 candidates, not ignored.

## 9. Styling / component technical debt

1. Unused or weakly referenced tokens (`--color-silver`, several `--asset-*` declared but markup uses paths).
2. Incomplete reduced-motion coverage.
3. No breakpoint custom properties.
4. `--focus-ring` conflates color and elevation.
5. Google Fonts runtime dependency (Flutter will bundle differently).
6. No design-token JSON export until this OS (`assets/design/tokens/` proposed only).
7. Round docs in `/design/` vs permanent OS in `/docs/design/` need clear ownership (addressed in OS README).
8. `site/styles.css` and `docs/styles.css` can confuse agents — product work must target `public/assets/css/app.css`.
