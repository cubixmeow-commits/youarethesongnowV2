Focused First Build Workshop

Facilitate the focused First Build Feature Workshop for YouAreTheSongNow V2 with CuBiX Meow and Brut.

PURPOSE
Turn the already-defined V2 goal into a precise, testable First Build Feature Contract. Do not design the product for us, start implementation, or reopen settled scope unless an owner explicitly asks to reconsider it.

Before asking questions, read the repo's AGENTS.md and the current project, decisions and workshop notes it requires—especially development-vault/05 Product Design/First Build Feature Workshop.md. Respect the authority hierarchy. The build freeze remains active.

ESTABLISHED STARTING POINT
- Rebuild/refine V1 functionality, not V1 code.
- Deliver the PHP/SQLite web application first.
- Follow it with a Flutter/Dart iOS client using the same PHP HTTP/JSON backend.
- First-build users have accounts, basic profiles, reusable portraits and credits.
- A user selects or enters a song and artist/band; the system obtains permitted lyrics or song context.
- The creative engine uses the strongest proven V1 prompting ideas and curated styles.
- The user chooses an image-quality level with a corresponding credit cost.
- Inexpensive models handle simple AI tasks; stronger models are reserved for work that needs them.
- Generation runs asynchronously and saves the image to the user's gallery.
- Gallery images can be downloaded or shared.
- Images may initially live on the application host; Backblaze B2 comes later.
- An approximately $20 monthly subscription, deliberate onboarding and a durable credit ledger belong in the invite-only beta.
- Additional credit-pack purchases and Backblaze B2 storage come soon after the core build functions.

FACILITATION RULES
- Ask one numbered owner-decision question at a time, in order unless an answer creates a better dependency order.
- Skip questions that become irrelevant.
- Do not silently decide for the owners or treat V1 behavior/provider preferences as V2 law.
- When an answer is vague, briefly establish: what the user sees, what they can do, what is stored, what failure looks like and what is deferred.
- Keep a decision ledger with the decision, exact behavior, dependencies, deferrals and unresolved details.
- Use FIRST BUILD, SOON AFTER, LATER, MAYBE / RESEARCH and NO / RETIRE only when classification helps.
- Do not repeatedly print the whole ledger. Summarize at meaningful section boundaries.

THE 35 DECISIONS

A. Release target and complete journey
1. Who receives the first deployed web build: owners only, invited reviewers/testers, or open registration?
2. What exact screens and decisions make up the happy path from arrival through the finished gallery image?
3. What smallest end-to-end result and reliability level proves the web build is ready for Flutter work?

B. Accounts, profiles and onboarding
4. How should users register/sign in, and what are the email-verification and recovery rules?
5. Which profile fields and editable settings exist initially?
6. What minimum explanation or guidance appears before a user's first generation?
7. Which account controls—account deletion, data export or sign-out-everywhere—are required, and what does deletion remove?

C. Song selection and lyrics
8. How does a user select a song: catalog search, artist/title entry, search-result confirmation or pasted link?
9. Which permitted source/provider supplies lyrics or song context, and what happens when nothing reliable is found?
10. How can a user correct a wrong match, cover/version or incomplete lyrics?
11. Are raw lyrics retained, discarded after analysis or replaced by derived Song DNA, and what is disclosed to users?

D. Creative engine and V1 prompt value
12. Which stages ship: interpretation, Song DNA, visual narrative, artist identity, portrait plan, scene composition, compiler, evaluation and retry?
13. Which proven V1 prompt behaviors/templates are preserved first, which contradictions are removed and which require experiments?
14. Which intermediate results, if any, can users see or edit?
15. How does artist/band visual identity affect output, and is it automatic, optional or cached?
16. Which personal-direction controls are allowed without becoming a generic prompt box?

E. Curated styles and image controls
17. Which initial V1-derived styles ship, how many are appropriate and do they need previews?
18. How are style prompts versioned, activated and maintained initially?
19. Which image controls are user-facing: orientation/aspect ratio, output count, portrait toggle or others?
20. What do the quality tiers mean in model/provider, output, approximate cost and credit price—and are three tiers justified?

F. Portrait experience and privacy
21. How many reusable portraits and people per generation are supported, with what file limits?
22. What is the minimum portrait-fidelity promise, and which wins when identity and composition conflict?
23. What happens when portrait generation fails, including retries, consent to remove a portrait and credit refunds?
24. Which privacy, metadata-stripping, deletion, consent and AI-provider disclosures protect portraits?

G. Generation jobs, providers and credits
25. Which first text/image providers and models perform which jobs, behind what replaceable adapter boundary?
26. What queued, running, progress and completion experience appears, and can users leave or cancel?
27. What retry limits, timeouts, safety handling and terminal failure behavior protect cost and quality?
28. How do subscriptions and complimentary access grant credits, and when are credits reserved, deducted or refunded?

H. Gallery, files and sharing
29. Which metadata and reusable settings appear on a gallery item?
30. Which actions ship: view, download, delete, regenerate/remix and reopen original settings?
31. Does web sharing mean download, device share sheet, private link or public link, and how is access revoked?
32. Which formats, sizes, retention, limits, backups and abstraction rules govern initial host storage and later B2 migration?

I. Flutter readiness, administration and freeze exit
33. Which account, portrait, song, generation-job, credit and gallery API operations—and auth/error conventions—must exist for Flutter?
34. What minimum owner/admin visibility is needed for users, credits, jobs, failures, costs, styles and provider usage?
35. What approved contract, provider/lyrics feasibility, privacy/cost choices, tests, deployment target and explicit authorization lift the build freeze?

FINAL OUTPUT
When all material decisions are resolved, produce a concise First Build Feature Contract covering:
1. Product promise and first users
2. Exact end-to-end journey and screens
3. Accounts, profiles and portraits
4. Song selection and lyrics
5. Creative-engine stages and preserved V1 prompt functionality
6. Styles, controls and quality tiers
7. Provider routing, job states, retries and failures
8. Subscription, complimentary-access and credit-ledger rules
9. Gallery, sharing and storage
10. PHP HTTP/JSON API requirements for Flutter
11. Minimum administration/operations
12. Privacy, security and deletion
13. Testable acceptance criteria and freeze-exit checklist
14. Explicit SOON AFTER, LATER, MAYBE / RESEARCH and NO / RETIRE lists
15. Remaining blockers
